anond — anonymized ClickHouse discovery & sandbox

Architecture reference · v1.1 cross-cluster target state · single-database mirror semantics (source mydb → sandbox mydb)

1. Overview

Large language models are excellent query and dashboard authors: given a schema and a feel for the data, they compose correct, idiomatic ClickHouse SQL and sensible visualizations. They are also untrusted with customer schema and data. A deployment that lets an LLM read system.tables or run free-form SELECTs against production has already disclosed every table name, column name, and — one query later — every value. The two properties conflict: the model needs to see the shape of the data to author well, and it must never see the data.

anond resolves the conflict with deterministic discovery plus HMAC tokenization plus a materialized, masked sandbox on a separate sandbox cluster. A trusted CLI job connects to the source cluster, profiles one database (schema, relations, workload mined from system.query_log), derives a stable token for every identifier via HMAC-SHA256, builds a per-column masking plan, and then materializes physical token-named tables — tbl_<hex> with col_<hex> columns — on the sandbox cluster, populated by masking SELECTs that run on the source and stream masked TSV across. The masking expressions, the HMAC key, the value seed, and the real-name map never leave the source side.

The untrusted LLM gets exactly two surfaces, both on the sandbox cluster: the tokens-only profile (catalog, columns, relations, workload shapes — every identifier tokenized) and the masked sandbox itself, which it can query with ordinary SQL. Joins, GROUP BYs, distributions, and time series behave like the real ones because masking is deterministic and type-preserving — so the model can iterate on real-feeling queries without a single real identifier or value in its context.

The artifacts the LLM composes — queries and dashboard specs written entirely over tokens — are handed to trusted instruments (Grafana, bentoclick, OpenAPI handlers). Because tokens occupy a lexically reserved namespace, de-tokenization is a word-level substitution against the source-side identifier_map; the instrument then runs the real SQL on the source cluster and routes real results to humans — never back to the LLM.

The classification produced by discovery drives the plan; an unknown type never falls through to "keep" — it falls out of the sandbox entirely.

6. Why a materialized sandbox, not masking views

A masking view leaks its own secrets. Any role with SELECT on a view can read the view body via SHOW CREATE VIEW and system.tables.create_table_query — verified live on ClickHouse 26.3. SQL SECURITY DEFINER only changes whose privileges the inner query runs with; the text stays readable. REVOKE SHOW cannot remove it, because SHOW is implicitly granted with any privilege. A view body containing sipHash64(<seed>, real_col) therefore hands the untrusted role both the value seed (making hashed join keys dictionary-attackable) and the real table and column names.

A materialized table is leak-resistant structurally: its SHOW CREATE exposes only token-named columns, types, and the engine clause. The masking expressions — seed plus real names — exist only in the job's source-side INSERT … SELECT, never in any object the untrusted role can read. Two further wins come free: exploration load lands on the sandbox cluster instead of production (the source pays only the one-shot materialization scan), and masked values are physically stored, so they can be ORDER BY keys — primary indexes work on masked predicates, where a view would compute the hash per row and full-scan.

7. Token scheme

Every identifier token is computed, never allocated:

HMAC-SHA256(key, kind || 0x00 || original) → kind_<8 hex>  (extended to 16 hex on collision; the decision is recorded in the manifest)

  • Idempotent and multi-replica safe. Re-runs and concurrent runs mint identical tokens with zero coordination; the identifier_map table is a materialization for trusted consumers to JOIN against, not an allocation ledger.
  • Lexically reserved namespace. The shape db_/tbl_/col_/… + hex is a valid unquoted ClickHouse identifier that must never collide with a real one: the run aborts if any real identifier matches the token pattern. (anond tags its own queries with log_comment='anond' and excludes them from mining precisely so its source-side masking SELECTs, which contain AS col_<hex> aliases, don't trip this guard on the next run.)
  • The reverse path needs no parser. Because tokens are reserved words, de-tokenizing LLM-composed SQL on the trusted side is a word-boundary substitution against the map — no SQL parsing in the security path.
  • One operator-controlled exception. When --dest-db equals the source DB name (mirror semantics, e.g. mydb → mydb), the DB-level name is operator-disclosed and kept verbatim so profile and sandbox agree. Tables and columns inside are always token-named.

8. Safety invariants

  • Never drop or replace a foreign object. Every name anond creates is registered in generated_objects first; if a name already exists and is not in the registry, ensureOurs aborts the run. cleanup drops exactly the registry list and nothing else — required since the sandbox DB name can be operator-chosen and no longer matches a token pattern.
  • Fail closed, everywhere. An unobserved identifier in a profile write is an error, not a passthrough. An unparseable SQL value is redacted whole (unbalanced quotes ⇒ [redacted]). An unknown or schemaless column type is excluded from the sandbox. The failure direction is always over-masking, never leaking.
  • Manifest-last run protocol. Every phase writes rows under a run_id; the manifest row is written last, so its presence is the completion marker. Consumers read only the latest complete run; a crashed run leaves no half-readable state.
  • Trusted split by construction. identifier_map and masking_plan exist only in the source cluster's meta DB; verification asserts the sandbox cluster's meta DB contains no trusted tables. A grants misconfiguration on the LLM-exposed cluster can de-anonymize nothing.
One-line summary. The boundary is a cluster, the enforcement is a GRANT, the tokens are pure functions of a key that never crosses, and every failure mode masks more — not less.
