1. The goal

An LLM agent (claude.ai, Claude Code, ChatGPT) should be able to browse a cluster's schema and write dashboard SQL without ever seeing real identifiers or real values. A human opening that same dashboard sees real data. The separation must hold even if the LLM is fully adversarial and the MCP server is the only thing standing between it and ClickHouse.

Two artifacts make this work:

  • anond — materializes a masked sandbox database claude_otel_anon from the real claude_otel: table/column names become HMAC tokens, values are masked. The LLM only ever queries this.
  • bentoclick — the dashboard SPA. The LLM authors panel SQL against the tokenized sandbox; a human opens the dashboard and the SPA runs the equivalent SQL as the human against real claude_otel.

2. Architecture at a glance

Two channels share one OAuth audience, one ClickHouse token directory, and one identical JWT claim. They differ only in which roles are active per request.

Purple = anon / LLM path  ·  Green = real / human path. Both authenticate to the same Auth0 audience and present the same JWT claim to the same CH token directory.

3. The anonymized sandbox

anond materializes claude_otel_anon from claude_otel:

  • Names are tokenized — table and column names become HMAC tokens (e.g. tbl_<hex>), so the schema itself leaks no business meaning.
  • Values are masked — the LLM sees shape and cardinality, not real identifiers.
  • The trusted token↔real map lives in a separate meta database (altinity), readable by the de-tokenization path but never by the LLM.
  • Alongside the masked tables, anond publishes profile tables (altinity.profile_*: catalog, columns, relations, shape, workload…) that give the LLM enough statistical context to author useful dashboards.

The LLM's default database is claude_otel_anon, and its active roles grant SELECT only there (plus the profile tables) — so even the schema it explores is the masked one.

4. One audience, one identity

Everything keys to a single audience: https://otel-mcp.demo.altinity.cloud/

  • MCP audience + public_resource_url (it is a pure OAuth resource server, broker:false).
  • ClickHouse token_processor expected_audience.
  • The bentoclick SPA requests this same audience (it talks to CH directly, but its JWT must validate against the same processor).
Pick the audience your MCP connector is already registered for. claude.ai is CIMD-registered against the MCP host. Pointing the audience at the CH host instead makes claude.ai see a new RFC 8707 resource and attempt a fresh registration that fails (mcp_registration_failed). Keep it at the MCP host value.

ClickHouse 26.x allows one <token> directory and one expected_audience per processor — so a single audience serves both channels. The channel split is done entirely by which roles are activated per request (§7), not by audience and not by user identity.

5. ClickHouse roles

Four roles, granted to every demo-org member identically. The LLM channel activates only the anon pair; the human channel uses all four (its default grant).

RoleGrantsChannel
oauth_otel_roleSELECT on claude_otel.*, system.*; SHOW DATABASEShuman — read real
bentoclick_viewer_roleSELECT on bentoclick.dashboards, dashboards_prefixhuman — read dashboards
anon_mcp_readerSELECT on claude_otel_anon.*, altinity.profile_*LLM — read anon
anon_author_roleINSERT on bentoclick.dashboards_raw; SHOW TABLES on bentoclick.*LLM — author dashboards

Real roles deliberately contain no anon substring, so the ^anon_ activation filter (§7) selects exactly the two anon roles and nothing else.

The token directory

ClickHouse provisions each user from a valid JWT (storage = token, no static user to shadow it) and assigns the claim's roles filtered by a safety regex. A static IDENTIFIED WITH jwt user would ignore the groups claim and keep its own grants — which is why the identity is left to the directory:

<token>
  <processor>auth0_otel</processor>
  <roles_filter>^(oauth_otel_role|bentoclick_viewer_role|anon_author_role|anon_mcp_reader)$</roles_filter>
</token>

Provisioned users get default_roles_all = 1 — their default (the human direct-CH path) is the full grant. The LLM never relies on defaults; the MCP narrows it per request.

6. The Auth0 Action — one stable claim for every channel

The post-login Action otel-bentoclick-claims (gated to the otel audience) mints the same claim regardless of client. It does not branch on client type and does not rewrite the username — both channels carry the real email and the full role set:

exports.onExecutePostLogin = async (event, api) => {
  const AUD = "https://otel-mcp.demo.altinity.cloud/";
  const aud = event.transaction?.requested_authorization_details?.[0]?.aud
           || event.transaction?.requested_resource_indicators?.[0]
           || event.resource_server?.identifier;
  if (aud !== AUD) return;                      // gate: otel audience only

  const NS = "https://mcp.altinity.cloud/", email = event.user?.email || "";
  if (email) {
    api.accessToken.setCustomClaim(NS + "email", email);                       // → currentUser()
    api.accessToken.setCustomClaim(NS + "email_verified", event.user.email_verified === true);
    if (event.user.name) api.accessToken.setCustomClaim(NS + "name", event.user.name);
  }
  // IDENTICAL on every channel. MCP activates only ^anon_ via role=;
  // bentoclick (direct CH) uses the full default grant.
  api.accessToken.setCustomClaim("https://clickhouse/roles",
    ["oauth_otel_role", "bentoclick_viewer_role", "anon_author_role", "anon_mcp_reader"]);
};
username_claim in CH is https://mcp.altinity.cloud/email, so the provisioned CH username is the real email on both channels. That is what makes currentUser() the real email — and dashboard owner-stamping (§9) free.

7. Per-request role activation in the MCP

The MCP is the only thing that makes the LLM channel anon. On every ClickHouse request it reads the role claim, filters it, and activates only the matching subset via repeated HTTP role= parameters — narrowing the user's (full) grant down to anon. Configuration:

server:
  oauth:
    role_claim:  https://clickhouse/roles   # JWT claim holding the role array
    role_filter: "^anon_"                    # activate only roles matching this regex
  • Narrows, never grants. role= can only restrict to roles the user already holds; it cannot escalate.
  • Fail-closed. If the filtered set is empty, the request is denied — it never falls back to the full default grant. role_filter is required whenever role_claim is set (validated at startup).
  • HTTP-only. Role activation rides the HTTP role= query parameter, so the MCP CH protocol must be http.
  • Works regardless of broker mode and independently of the auth wire format (it is applied post-authentication).

Implemented in altinity-mcp as oauth.role_claim / oauth.role_filter (PR #141). The bentoclick human path does not go through the MCP, so it keeps the full default grant and sees real data.

8. Why this is correct & safe

No role-thrash race

The CH token directory rewrites a user's granted roles on each login only if the claim differs from what's stored. Because the Action emits the identical full claim on every channel, the stored entity never changes after first login — it is immutable in steady state. Concurrent claude.ai and bentoclick logins cannot perturb each other's grants. The per-channel difference lives on the request (role=), not on the shared user entity.

The LLM cannot escalate to real roles

Even though the LLM's identity is granted the real roles, it is held to anon because:

  • The MCP pins role=^anon_ on every request and fails closed on an empty set.
  • ClickHouse HTTP is single-statement and the MCP holds no session, so the LLM cannot issue SET ROLE oauth_otel_role; SELECT ….
  • The query tool is read-only (a second backstop).
Accepted trade-off. "The LLM never sees real data" is MCP-enforced, not pure CH RBAC — the LLM's identity is granted the real roles and is anon only because the MCP activates the anon subset. The mitigations above (fail-closed activation, single-statement HTTP, no session, read-only tool) are what make this safe. The upside is that currentUser() is the real email everywhere, which makes owner-stamping free.

9. Dashboard owner-stamping

The dashboard pipeline is: bentoclick.dashboards_raw (Null engine) → dashboards_mv (SQL SECURITY DEFINER, stamps currentUser() AS owner) → bentoclick.dashboards. Because currentUser() is the real email on every channel, an LLM-saved dashboard is stamped with the human's email and appears under /b/v/<email>/<slug> — no MCP injection, no owner column, no MV change.

Required setting: async_insert=0 on the save path. The otel cluster defaults to async_insert=1. With async insert, the INSERT is buffered and flushed by a background thread whose context has an empty ClientInfo — so currentUser() (and any DEFAULT/MATERIALIZED/ALIAS expression, and currentUser() inside the DEFINER MV) evaluates to an empty string, silently blanking the owner. The fix is to force synchronous insert on the MCP's CH connection — the MCP's only writes are tiny dashboard saves, which never need async batching:

config:
  clickhouse:
    extra_settings:
      async_insert: "0"
This was root-caused to AsynchronousInsertQueue::processData building the flush context from the global context and restoring only the access identity (never the ClientInfo user fields). Reported upstream as ClickHouse #107530.

10. De-anonymized human view (detok)

The LLM authors panel SQL over the masked sandbox (claude_otel_anon.tbl_…, col_…). For the human to see real data, that SQL is de-tokenized at the dashboard read path: the dashboards_mv (DEFINER) wraps the stored panel SQL with the detok() UDF, so bentoclick.dashboards holds real-name SQL that the /b/ SPA runs against real claude_otel.

detok() rewrites, via the altinity.token_to_real dictionary:
  col_530b0876            → Timestamp
  col_5ab2d3a7            → LogAttributes
  claude_otel_anon.tbl_5f5c0ed2 → claude_otel.otel_logs

The DEFINER (bentoclick_definer) needs GRANT dictGet ON altinity.token_to_real. The LLM keeps seeing tokens (it has no read on bentoclick.dashboards); only the human read path is de-tokenized.

The load-bearing rule: detok() de-anonymizes NAMES, not VALUES. Two consequences shape what the LLM may write:
  • GROUP BY de-anonymizes for free; FILTER does not. Because attrmap keys are always real and the human re-runs against real data, GROUP BY on any key relabels masked values to real automatically. But a WHERE k = 'literal' filtering on a masked value matches nothing in real data. So only values the LLM filters on must be real in the sandbox.
  • Per-key roles decide masking AND guidance. anond auto-classifies every attribute KEY into a role (PII denylist first, then value cardinality / numeric-fraction): vocabulary (low-card categorical, e.g. event.name, model) → value kept real (filter & group); measure (numeric, e.g. *_tokens, cost_usd) → kept (aggregate); identity (user.email, organization, *.id) → masked, GROUP BY only; sensitive (high-card free text) → masked. A "by user" panel must GROUP BY LogAttributes['user.email'] (relabels to real emails for the human) — never user.id, a source-side SHA256 (not our masking, not reversible). The role of each key is published to the LLM via describe_attributes.

Classification: PII denylist (catches low-card-but-sensitive keys like organization) overrides cardinality; a manual --keep-attr-keys override still exists. Tunables: --attr-card-threshold (default 64), --pii-key-pattern.

11. MCP tools & discovery

The otel MCP exposes exactly what the bentoclick authoring loop needs — read, discover, save. The discovery tools are cluster-sourced (a commented view in the cluster becomes the tool; no domain knowledge in MCP config):

ToolBackingPurpose
execute_querystatic (read-only)run SELECTs against the sandbox
describe_schemaview altinity.schema_guidetokenized schema map: table role + per-column class + usage hint (the COMMENT teaches the class contract)
describe_attributesview altinity.attr_guideper Map-key role (vocabulary/identity/measure/sensitive) + usage — so the LLM filters vocabulary, GROUP BYs identity, aggregates measures, avoids sensitive
get_dashboards_prefixview bentoclick.dashboards_prefixthe correct share-URL prefix …/b/v/<email>/ — the LLM must call this, never guess /v/
save_dashboardinsert → bentoclick.dashboards_rawsave a dashboard (→ detok MV → dashboards)

There is no generic write_query tool — the only write is the dashboard save. Tool names match the bentoclick-dashboard skill. Discovery runs per request as the LLM's role, so each backing view must be SELECT-able by anon_* (e.g. GRANT SELECT ON bentoclick.dashboards_prefix TO anon_author_role).

12. Deployment configuration

MCP — deploy/otel/mcp-values.yaml (key fields)

config:
  clickhouse:
    host: clickhouse-{cluster}.demo.svc.cluster.local
    port: 8123
    protocol: http                 # required: role= activation is HTTP-only
    database: claude_otel_anon      # LLM's default DB is the masked sandbox
    extra_settings:
      async_insert: "0"             # synchronous saves → owner-stamping works (§9)
  server:
    oauth:
      enabled: true
      broker: false                 # pure OAuth resource server
      issuer:   https://altinity.auth0.com/
      audience: https://otel-mcp.demo.altinity.cloud/
      public_resource_url: https://otel-mcp.demo.altinity.cloud/
      role_claim:  https://clickhouse/roles
      role_filter: "^anon_"
    tools:                                  # read + discover + save; NO generic write
      - { name: execute_query,        type: read }
      - { name: describe_schema,      type: read,  view_regexp: ^altinity\.schema_guide$ }
      - { name: describe_attributes,  type: read,  view_regexp: ^altinity\.attr_guide$ }
      - { name: get_dashboards_prefix, type: read, view_regexp: ^bentoclick\.dashboards_prefix$ }
      - { name: save_dashboard, type: write, mode: insert, table_regexp: ^bentoclick\.dashboards_raw$ }

ClickHouse — native token auth (Antalya 26.3, no sidecar)

<token_processors>
  <auth0_otel>
    <type>openid</type>
    <configuration_endpoint>https://altinity.auth0.com/.well-known/openid-configuration</configuration_endpoint>
    <expected_audience>https://otel-mcp.demo.altinity.cloud/</expected_audience>
    <username_claim>https://mcp.altinity.cloud/email</username_claim>
    <groups_claim>https://clickhouse/roles</groups_claim>
    <token_cache_lifetime>60</token_cache_lifetime>
  </auth0_otel>
</token_processors>

Deploy

helm upgrade otel-mcp /path/to/altinity-mcp/helm/altinity-mcp \
  -f deploy/otel/mcp-values.yaml -n demo
kubectl rollout restart deploy/otel-mcp-altinity-mcp -n demo   # also clears per-pod auth cache
kubectl rollout status  deploy/otel-mcp-altinity-mcp -n demo

The claude.ai connector points at the multicluster route https://otel-mcp.demo.altinity.cloud/mcp/otel.

13. Verification checklist

  1. Identity: LLM SELECT currentUser() → the real email.
  2. Active roles: LLM SELECT currentRoles() → ['anon_author_role','anon_mcp_reader'] only.
  3. Anon read: LLM reads tokenized tables in claude_otel_anon ✓.
  4. No real data: LLM SELECT … FROM claude_otel.otel_logs → ACCESS_DENIED (497).
  5. Owner-stamping: LLM saves a dashboard → bentoclick.dashboards.owner = <real email>.
  6. Human real (detok): the saved dashboard's stored panels reference claude_otel.otel_logs / LogAttributes (no tokens); /b/v/<email>/<slug> renders real numbers, and "by user" shows real emails (GROUP BY user.email).
  7. Share URL: get_dashboards_prefix → …/b/v/<encoded-email>/ (not /v/).
  8. Fail-closed: an empty filtered role set → MCP returns access-denied (it never falls through to the full grant).

14. Operating it

Add a human: Auth0 → Organizations → demo → add member → assign oauth_otel_role + bentoclick_viewer_role (org membership is the hard allowlist; the token directory provisions them on first login).

Add an MCP client: just connect it to https://otel-mcp.demo.altinity.cloud/mcp/otel. It registers via CIMD and is anon automatically — nothing per-client to configure.

Current design (anonymized-LLM dashboards on otel). Source of truth for live values: acm/mcp/deploy/otel/mcp-values.yaml, the Auth0 Action auth0-actions/otel-bentoclick-claims.js, and the CH token-processor / user-directory ACM settings. Owner-stamping depends on async_insert=0 (ClickHouse #107530).
