1. Summary & framing

We need to evolve or fork Altinity/altinity-mcp into a full-featured AI Gateway in front of a fleet of ClickHouse clusters with business data — a single control plane that LLM agents, dashboard authors, and end-users hit, brokering identity, scope, role, and least-privilege access into many downstream ClickHouse deployments.

BentoClick is the product name for the dashboard surface added on top. It is not a from-scratch backend. The AI-Gateway framing matters because it sets the security posture for the whole design:

  • The gateway sits in front of many customer ClickHouse clusters — multi-cluster from day one.
  • Downstream data is business data — payments, customer records, operational telemetry. Defaults conservative, opt-in explicit, least-privilege enforced at the gateway and at ClickHouse.
  • LLM agents (claude.ai, ChatGPT, internal agents) are first-class clients alongside browsers. The MCP surface is not a side feature.

2. What altinity-mcp already provides

Most of the gateway machinery already exists. BentoClick inherits it unchanged.

  • OAuth resource-server posture (PR #110 — "redefine gating mode as pure OAuth resource server"). External AS owns DCR, /authorize, /token, refresh rotation, reuse detection, revocation. altinity-mcp validates incoming AS-issued JWTs (signature + RFC 8707 audience byte-equality + expiry) and authorizes per-tool scopes.
  • Cluster-secret + impersonation chain in pkg/clickhouse/client.go, exercised by cluster_secret_test.go. Used today; preserved for forward-mode and non-dashboard MCP. Not on BentoClick's dashboard data path under this proposal.
  • Per-query role binding via the Altinity clickhouse-go fork feature/interserver-extra-roles @ 3e22df3 (bumps DBMS_TCP_PROTOCOL_VERSION to 54472).
  • altinity.mcp_role_metadata whitelist (#107) — operator-curated set of CH roles surfaced to the consent screen.
  • Refresh-token reuse-detection design in CH MergeTree (#106). Deferred for v1 (external AS handles it). Ready if MCP re-enters AS territory.
  • Dynamic MCP tools from CH schema (pkg/server/server_dynamic_tools.go), MCP resources, execute_query, schema discovery.
  • Fail-closed discipline: startup refusal on misconfiguration, ERR + 500 on state failures, no graceful degradation.

3. What BentoClick adds

  • Dashboard CRUD, sanitization boundary, validate / preview / publish flows.
  • Sharing (pinned-version-by-default share links).
  • SPA serving with versioned runtime artifacts and available_on_nodes tracking.
  • Dashboard MCP tool family, additive to altinity-mcp's existing surface.
  • Dedicated control-plane ClickHouse for gateway state (dashboards, shares, audit, artifact registry).
  • Multi-cluster dashboard model: each dashboard targets one connected CH cluster, identified by connection_id.
  • The JWT verifier sidecar as a separately-deployable component for OSS CH installations.
What BentoClick deliberately does not add in v0.2. Multi-tenant orgs/teams, folder/project hierarchy, viewer/editor roles, ownership transfer — all v1.x. Dashboards have a single owner. org_id columns are reserved on every table with a 'default' fallback, so the migration to real tenancy is additive when it lands. Realistic BI workflows will hit this limit fast; this is a v0.2 scoping choice, not a permanent stance.

4. Identity & the sidecar

BentoClick does not mint, hold, or proxy any data-plane credential. The flow is OAuth-textbook: user authenticates at the AS, receives a JWT, presents the JWT directly to ClickHouse. ClickHouse validates it.

4.0 One identity, many tokens

RFC 8707 audience binding is byte-equal. One JWT cannot serve both aud=bentoclick-api and aud=ch:cluster-1. The same user session yields multiple access tokens, one per resource the user touches:

  • aud=bentoclick-api for BentoClick's dashboard/sharing/MCP endpoints.
  • aud=ch:cluster-1, aud=ch:cluster-2, … per CH cluster the user queries.

The AS issues all of these from one underlying refresh-token chain. The token-helper manages a per-(resource, scope) cache and the SPA does the same. Each call to bentoclick token --audience=ch:cluster-1 returns a different JWT than bentoclick token --audience=bentoclick-api, with identical sub/email but distinct aud.

This is what the altinity-mcp #104 hardening already enforces on the validation side; v0.2 makes the issuance side match.

4.1 The JWT verifier sidecar

A small single-binary stateless validator. ~300 LOC of Go. Hardened deployment surface: read-only filesystem, listens on a unix socket or loopback, outbound network to AS JWKS only, no in-process state about users.

Wire shape

ClickHouse → sidecar:

POST /verify HTTP/1.1
Host: 127.0.0.1:9999
Authorization: Basic <base64(boris@altinity.com:<JWT>)>

Sidecar → ClickHouse on success:

200 OK
Content-Type: application/json
{
  "settings": {
    "readonly": "1",
    "max_memory_usage": "10000000000"
  }
}

The response body is parsed by CH's SettingsAuthResponseParser (src/Access/SettingsAuthResponseParser.cpp): JSON with an optional settings object whose key/values are applied as session settings via settingStringToValueUtil. A bare 200 with no body is sufficient for "auth OK." The response cannot carry roles — see §4.2.

On failure: any non-200 status. The body may carry a structured error with a stable error_class (expired, bad_audience, signature_invalid, user_mismatch, scope_missing) for the sidecar's own log; CH only cares about the status code.

Common misconception. CH's http_authentication response format does not support per-session roles. It only supports session settings (e.g. readonly, memory and complexity caps). Role binding is handled out-of-band via the URL ?role= parameter and CH RBAC — see next subsection.

Validation steps

  1. Parse Basic header. Extract user, password = JWT.
  2. Decode JWT header for kid. Look up cached JWKS; JIT-refresh on miss.
  3. Verify signature with the matched key.
  4. Verify iss exact-match, aud byte-equal (RFC 8707), exp, nbf.
  5. If email_verified claim present, require true.
  6. Compare username claim against Basic user. Strict by default.
  7. Verify required scope present.
  8. Optionally derive session settings from the JWT (e.g. readonly: 1 if scope is read-only).
  9. Return 200 with optional {"settings": {...}} body. Not roles — role binding is handled out-of-band (§4.2).

Every step is local. No outbound network call per request after JWKS is cached.

Config sketch

listen:
  unix: /run/ch-jwt-verify/sock

as:
  issuer: https://as.example.com
  jwks_url: https://as.example.com/.well-known/jwks.json
  jwks_cache_ttl: 5m
  jwks_refresh_ahead: 1m

expected_audience: ch:cluster-1

identity:
  username_claim: email
  match_mode: lowercase_equal
  require_email_verified: true

authorization:
  required_scope: data:read
  # Note: no roles_claim here. Role binding is via URL ?role= (OSS)
  # or JWT groups claim consumed natively by CH (Antalya). See §4.2.

settings_from_scope:
  # Optional: map JWT scopes to session settings the sidecar returns.
  data:read:
    readonly: "1"

cache:
  result_cache_ttl: 30s
  negative_cache_ttl: 5s

4.2 Role binding

CH's http_authentication response can carry session settings but not roles. Role selection happens elsewhere — and the right "elsewhere" differs by deployment and by who's driving the client. The threat surface is asymmetric:

  • LLM agents (MCP path): we don't trust the agent to honor the user's consent choice. Role binding must be enforced server-side, in a place the agent cannot manipulate.
  • Human-driven clients (Python notebook, DBeaver, SPA): the consenter and the query-issuer are the same person. There is no consent to violate — the human picks roles within their granted set, and CH RBAC is the only ceiling needed.

This gives a clean two-by-two:

DeploymentMCP path (untrusted client)Direct clients (human)
Antalya 26.1+ JWT groups claim → CH external_roles → RBAC ceiling. Agent cannot expand. strong Same JWT flow. strong
OSS + sidecar MCP server pins ?role=<consent_role> on the CH URL; agent has no surface to override. strong by enforcement at the gateway Client appends ?role= from its JWT claim; CH RBAC bounds. acceptable — human is the consenter

How ClickHouse applies ?role=

Verified in src/Server/HTTPHandler.cpp:236-238:

auto roles = params.getAll("role");
if (!roles.empty())
    context->setCurrentRoles(roles);

Multiple ?role=a&role=b supported. setCurrentRoles rejects with access-denied if the user isn't actually granted the role. URL-supplied role is always a narrowing directive, never an escalation. CH RBAC + the altinity.mcp_role_metadata whitelist (#107) + DEFAULT ROLE NONE ensure the ceiling is operator-curated.

Antalya's group→role binding (native JWT path)

Confirmed in origin/antalya-26.1 source — this is an Antalya feature, not in upstream OSS:

  • src/Access/TokenProcessorsJWT.cpp:399-400 — JWT's groups_claim populates credentials.setGroups(...).
  • src/Access/ExternalAuthenticators.cpp:622 — cache_entry.external_roles = credentials.getGroups().
  • src/Access/ContextAccess.cpp:370-373 — external_roles merged into current_roles, intersected with granted_roles.findGrantedWithAdminOption(*params.external_roles).

On Antalya, the JWT is the role binding: AS embeds groups in the JWT, CH applies them as the active role set, intersected with what the user is granted. Clients have no opportunity to expand. Strong consent-binding for free.

MCP-side enforcement (OSS path)

altinity-mcp/BentoClick already holds the JWT and the consent context per session. It builds the URL on the agent's behalf, never letting the agent pick the ?role= value. The MCP server is the enforcement point; the agent has no tool argument that influences role selection. 

// pkg/clickhouse/client.go — sketch
func (c *Client) ExecuteQueryHTTP(ctx context.Context, sess *Session, sql string) (...) {
    u := c.baseURL
    u.RawQuery = url.Values{
        "role": []string{sess.ConsentRole},   // enforced here, not agent-controllable
    }.Encode()
    // POST sql to u with X-ClickHouse-User: sess.User,
    //                   X-ClickHouse-Password: sess.JWT
}

Same enforcement boundary altinity-mcp already uses for scope-to-tool gating in #107. Dynamic tools (pkg/server/server_dynamic_tools.go) and MCP resources go through the same client and inherit the same role pinning, so schema discovery also runs as the consent role — the agent sees the schema the consent role can read.

HTTP protocol only. ?role= is a CH HTTP-handler primitive. Native protocol (port 9000) needs SET ROLE 'name' SQL after connect, which is awkward with pooled connections. v0.2 standardizes on the CH HTTP protocol for the BentoClick story. clickhouse-connect (Python), HTTP-mode JDBC, and the SPA fetch are all native-fit; native-protocol clients (clickhouse-driver) need the SET ROLE workaround.

5. OSS / Antalya parity

From BentoClick's perspective, OSS ClickHouse and Antalya/Cloud ClickHouse are identical: in both cases, BentoClick is out of the data-plane auth path and the client's JWT is presented directly to ClickHouse. The only difference is on the CH-side ops: OSS deploys a sidecar; Antalya validates natively.

6. Client access patterns

The architecture only works if real clients can actually obtain and present JWTs. Most clients can't speak OAuth natively, but they all accept a username and a password — and a JWT in the password field is fine. The problem reduces from "redesign every CH client for OAuth" to "how does the client obtain a JWT."

6.1 Per-client breakdown

ClientPatch neededMechanism
clickhouse-connect (Python) None Companion library calls helper or runs OAuth in-process; passes JWT to driver
clickhouse-driver (Python) None Same companion library
ClickHouse JDBC Optional auth-provider extension Helper-CLI + file-on-disk works today; driver extension is the long-term polish
DBeaver / DataGrip None Inherits JDBC; "external command" password field reads from helper
clickhouse-client CLI None --password "$(bentoclick token)"
Superset Light SQLAlchemy auth callback Service identity via client_credentials grant; one JWT, one narrow CH role
Grafana Datasource plugin config Same service-identity pattern as Superset
The only structurally important patch is the JDBC auth-provider extension. Everything else is a thin glue library or a deployment-time configuration choice.

6.2 Picking the role on direct-client calls

CH's HTTP handler reads ?role= (verified in HTTPHandler.cpp:236-238). The question per client is whether the driver exposes a way to set that URL parameter cleanly. This needs implementation testing per driver, not aspirational examples. Honest current status:

ClientMechanism (needs verification)Risk
HTTP-mode JDBC URL Append &role=... to JDBC URL; HTTP-mode driver should forward as query param Needs driver test; some JDBC drivers reserve known param names and may eat role
clickhouse-connect (Python, HTTP-only) Pass through driver's http_params / query_params mechanism; not via settings={} (no role setting exists) Earlier draft was wrong — verify the right API in the driver
clickhouse-client CLI Native protocol — --param_role sets a SQL parameter named role, not the CH role. Use SET ROLE 'name' in a startup SQL, or HTTP mode Earlier draft was wrong
clickhouse-driver (Python, native) Execute SET ROLE 'name' after connect; document pool gotcha Pool reuse without re-SET leaks role across logical sessions
SPA fetch() Append ?role=... to URL; standard Low — URL-building is direct
Implementation status: needs per-driver test pass. Earlier sketches in this doc asserted driver behavior that was wrong (--param_role, settings={"role":...}). The corrected position: only the HTTP-mode SPA fetch path is known to work. Every other client needs a small integration test against a real CH instance before being recommended.

CH RBAC bounds whatever the client asks for. A human who picks a role they aren't granted gets access_denied from CH, not a security incident.

6.3 Token refresh during long-lived sessions

  • HTTP protocol: each query is a fresh authentication. The helper rotates the JWT between queries.
  • Native protocol: connection-level auth. Open connections survive token expiry; reconnects need a fresh JWT.
  • JDBC connection pools that cache the password at pool init are the footgun. The auth-provider extension fixes it; until then, document the pool config gotcha (short pool TTL or auth-on-checkout).

7. Storage model

All gateway state lives in a dedicated control-plane ClickHouse with Keeper. Engine choice tracks the consistency requirement.

EmbeddedRocksDB is not used. It is a server-local engine that does not replicate across CH replicas — drafts written on one replica would not appear on another. KeeperMap fits the same point-lookup + UPSERT shape and replicates correctly. (Same concern #106 raised for refresh-state.)

7.1 Schema

-- Drafts: mutable, point lookup, replicated via Keeper.
CREATE TABLE dashboards_drafts (
  dashboard_id  String,
  owner_user_id String,
  org_id        String DEFAULT 'default',  -- reserved for v1.x tenancy
  name          String,
  description   String,
  spec_json     String,
  updated_at    DateTime64(3),
  deleted_at    Nullable(DateTime64(3))
) ENGINE = KeeperMap('/bentoclick/drafts')
PRIMARY KEY dashboard_id;

-- Versions: append-only history. Audit / "show me past versions" only.
-- Eventually consistent across CH replicas (ReplicatedMergeTree replication is async).
-- Readers never join from published_dashboards into this table on the hot path.
CREATE TABLE dashboard_versions (
  version_id       String,
  dashboard_id     String,
  version_number   UInt64,
  spec_json        String,
  runtime_version  String,
  created_by       String,
  org_id           String DEFAULT 'default',  -- reserved for v1.x tenancy
  created_at       DateTime64(3)
) ENGINE = ReplicatedMergeTree
ORDER BY (dashboard_id, version_number);

-- Published state: full current spec, atomic via KeeperMap.
-- This is the source of truth for "render this dashboard now."
-- Eliminates the publish-atomicity race between MergeTree + KeeperMap.
CREATE TABLE published_dashboards (
  dashboard_id        String,
  current_version_id  String,            -- references dashboard_versions (audit link)
  spec_json           String,            -- full current spec, denormalized for atomic read
  runtime_version     String,
  owner_user_id       String,
  org_id              String DEFAULT 'default',
  updated_at          DateTime64(3)
) ENGINE = KeeperMap('/bentoclick/published')
PRIMARY KEY dashboard_id;

-- Shares: needs immediate revocation visibility.
-- Distinguishes three things that were previously conflated:
--   pinned_version_id    : which dashboard spec the recipient sees
--   data_mode            : snapshot | live | live_authenticated
--   identity_mode        : recipient_auth | owner_credential | service_identity
CREATE TABLE shares (
  share_id          String,
  dashboard_id      String,
  org_id            String DEFAULT 'default',
  pinned_version_id Nullable(String),               -- spec frozen at share-creation
  data_mode         Enum8('snapshot'=1,             -- query results frozen at share-creation (default)
                          'live'=2,                  -- live queries, recipient must auth
                          'live_authenticated'=3),   -- live queries via owner's stored credential
  identity_mode     Enum8('recipient_auth'=1,
                          'owner_credential'=2,
                          'service_identity'=3),
  owner_user_id     String,
  token_hash        String,
  snapshot_ref      Nullable(String),               -- pointer to snapshot rows if data_mode=snapshot
  created_at        DateTime64(3),
  revoked_at        Nullable(DateTime64(3)),
  expires_at        Nullable(DateTime64(3)),
  last_used_at      Nullable(DateTime64(3)),
  label             Nullable(String)
) ENGINE = KeeperMap('/bentoclick/shares')
PRIMARY KEY share_id;

-- Snapshot data for shares whose data_mode='snapshot'.
-- One row per panel per snapshot. Results inlined as JSON.
-- Size bounds enforced at snapshot time (max rows × panels × byte cap).
CREATE TABLE share_snapshots (
  snapshot_ref   String,
  panel_id       String,
  result_json    String,
  rendered_at    DateTime64(3),
  expires_at     Nullable(DateTime64(3))
) ENGINE = ReplicatedMergeTree
PARTITION BY toYYYYMMDD(rendered_at)
ORDER BY (snapshot_ref, panel_id);

-- Runtime artifact registry.
CREATE TABLE runtime_artifacts (
  version            String,
  path               String,
  manifest_json      String,
  available_on_nodes Array(String),
  created_at         DateTime64(3),
  disabled_at        Nullable(DateTime64(3))
) ENGINE = ReplicatedReplacingMergeTree(created_at)
ORDER BY version;

-- Audit: high-volume append-only, partitioned by day.
CREATE TABLE audit_events (
  event_id      String,
  actor_user_id String,
  event_type    LowCardinality(String),
  target_type   LowCardinality(String),
  target_id     String,
  metadata_json String,
  request_id    Nullable(String),
  created_at    DateTime64(3)
) ENGINE = ReplicatedMergeTree
PARTITION BY toYYYYMMDD(created_at)
ORDER BY (created_at, event_type);

-- Distributed leader locks (artifact GC, audit compaction).
CREATE TABLE leader_locks (
  lock_name    String,
  holder_node  String,
  acquired_at  DateTime64(3),
  expires_at   DateTime64(3)
) ENGINE = KeeperMap('/bentoclick/locks')
PRIMARY KEY lock_name;

8. Dashboard rendering path

Who actually executes the SQL behind a rendered dashboard? Three real options, used in different combinations depending on viewer type. This is the most consequential open architectural decision in v0.2 and worth surfacing explicitly.

OptionOwner viewing own dashboardShare recipientMajor costs
A. Browser → CH directly SPA holds owner's aud=ch:cluster-N JWT; queries each panel via fetch Recipient may have no CH identity — broken unless they log in to AS and have CH grants CORS on every customer CH · CH endpoint discoverable from browser · JWT in browser memory (XSS = CH access) · private-network CH unreachable from recipient's browser
B. BentoClick proxies live queries BentoClick on path, uses owner's JWT to upstream CH BentoClick uses owner's stored credential, service identity, or recipient's JWT depending on identity_mode Streaming HTTP proxy reappears with full conn-pool/cancellation/backpressure surface (the 1500-LOC concern) · per-user CH audit weakens when service identity is used
C. Snapshot at share-creation (Owner uses A or B for live editing — snapshot is irrelevant for owner) BentoClick executes panels once at share time; results stored in share_snapshots; recipient sees frozen data Snapshot storage with size caps · "live data" lost (often a feature for shares)

8.1 v0.2 default policy

  • Owner viewing own dashboard: option A. Owner's browser holds owner's aud=ch:cluster-N JWT; SPA queries CH directly. CORS configured at deployment time per cluster.
  • Share recipient — default: option C. Default data_mode='snapshot'. Recipient sees frozen results, no live query, no CH identity required. This is how most BI sharing already works (Tableau Public, Looker Studio).
  • Share recipient — live, opt-in: option B with data_mode='live' and identity_mode='recipient_auth'. Recipient must authenticate via AS; BentoClick proxies the recipient's JWT to CH. We pay the streaming-proxy LOC cost here because neither A (no CH identity at recipient) nor C (live needed) fits.
  • Share recipient — live with owner credential: option B with identity_mode='owner_credential'. Disabled by default; requires explicit deployment-config opt-in because it breaks per-user audit (CH sees owner identity for all queries).
The streaming-proxy code reappears for live shares. The earlier "sidecar is <300 LOC" argument applies only to authentication. Live share rendering needs an HTTP proxy in BentoClick with connection pooling, streaming, cancellation, backpressure. Confined to that single feature, not a general data-plane proxy.

8.2 Browser → CH direct: deployment requirements

  • Each CH cluster's HTTP endpoint must allow CORS for the BentoClick SPA origin.
  • CH endpoints must be reachable from the user's browser (public IPs or VPN/zero-trust).
  • SPA discovers CH endpoint URLs via BentoClick's connection metadata API.
  • JWT TTL kept short (≤1h) to bound XSS-stolen-token reuse.
  • CSP forbids inline script, eval, untrusted URL schemes.

9. Dashboard lifecycle

PhaseWhereNotes
Draftdashboards_drafts (KeeperMap)Mutable, owner-scoped. LLM agents may write via MCP.
ValidateIn processSchema + panel-type checks. Optional EXPLAIN through viewer's CH identity.
PreviewIn processOwner-only. No public share link.
Publishdashboard_versions + published_dashboardsAppend-only version row + atomic pointer update.
Shareshares (KeeperMap) + share_snapshots (MergeTree) when data_mode='snapshot'Three orthogonal axes: pinned spec · data mode (snapshot / live / live_authenticated) · identity mode. Default: pinned + snapshot + recipient_auth. Revocable.
Share-link semantics — three independent axes:
  • Pinned spec (pinned_version_id): which dashboard definition the recipient sees. Pinned by default; "follow latest" is opt-in.
  • Data mode (data_mode): snapshot (frozen results at share time, default), live (recipient-authenticated live query), or live_authenticated (owner-credential live query, deployment opt-in).
  • Identity mode (identity_mode): which credential executes any live queries — recipient_auth, owner_credential, or service_identity.
Pinned spec alone is not enough to make a share safe — a later publish doesn't change the spec the recipient sees, but new rows landing in CH still affect live queries. data_mode='snapshot' is the only mode that fully freezes what the recipient observes.

10. Sanitization & validation

The v0.1 SECURITY DEFINER materialized view chokepoint is reimplemented in Go as pkg/dashboards/sanitize.go. There is exactly one write path for specs. No admin override. No MCP back door. The 90% test-coverage gate already in CLAUDE.md applies here.

10.1 Validation without execution

  • JSON schema check against versioned spec_version.
  • Required-field and panel-type constraint checks.
  • Runtime-compatibility check (spec matches declared runtime_version).
  • Optional EXPLAIN through viewer's CH identity — catches broken SQL pre-publish without leaking schema access beyond what the user already has.

10.2 SPA renderer posture (defense in depth)

The sanitizer at write time is the canonical safety boundary, but renderers are not permitted to do unsafe things even with sanitized input:

  • No innerHTML of arbitrary spec content. Use textContent for strings.
  • No javascript: or data: URL schemes from spec — validate against an allowlist (https:, http: optionally, mailto:).
  • No arbitrary <script>, <iframe src=...>, or event-handler attributes from spec content.
  • No eval or new Function() on spec content.
  • Markdown rendering, if any, goes through a sanitizing markdown library (no raw HTML pass-through).

Strict CSP enforced at the SPA origin: script-src 'self', no 'unsafe-inline', no 'unsafe-eval', restricted connect-src for CH endpoints. This way even a renderer bug that echoes injected content cannot execute it.

The principle is "one canonical sanitizer at write time, defense-in-depth at render time." The renderer never relies on sanitization alone — sanitization is the floor, not the ceiling.

13. HA validation chain

BentoClick replicas are stateless per-request. Any replica can serve any request. Sticky sessions are not required.

StateWhereHow HA works
AS public keysPer-replica memory cacheTTL refresh against AS JWKS; all replicas converge on AS's published keys
User identityJWT claimsEach request self-describing; no shared state needed
Role allowlistaltinity.mcp_role_metadata (control-plane CH)All replicas read same CH
Dashboard versions, audit, artifactsReplicated MergeTreeCH replication
Drafts, shares, published pointer, locksKeeperMapKeeper replication; immediate cross-replica visibility
Audit witnessExternal append-only sinkSink owns durability
JWE-to-random-replica is a non-question in v1. BentoClick does not issue JWEs. The external AS issues signed JWTs; any replica validates them by public-key crypto against the AS's JWKS. No shared secret on the BentoClick side, no cross-replica coordination. The dormant JWE machinery in pkg/jwe_auth/ would become relevant only if BentoClick re-enters AS territory (v2/v3 per the v1-scope notes on #106/#107). At that point HA would require shared JWE key material loaded from deployment config or KeeperMap with kid-keyed lookup.

14. Threat model & residual risk

13.1 In scope

  • Anonymous access — rejected (resource-server gates everything).
  • AS-issued JWT tampering — rejected (signature + audience check).
  • XSS in the SPA — short JWT TTLs, strict CSP (no 'unsafe-inline', no eval), sanitization at one boundary, defense-in-depth in renderers (no innerHTML of spec content, URL scheme allowlist). The browser-direct-to-CH rendering path (§8) does mean an XSS in the SPA exposes the user's aud=ch:cluster-N JWT — accept this risk with short TTLs and strict CSP, do not enable bypass-mode features that lengthen TTL.
  • Confused-deputy via DCR'd client — addressed by altinity-mcp's consent screen (#107).
  • Refresh-token theft — owned by the external AS.
  • Share-link leakage — revocable (KeeperMap immediate-revoke), optional expiry, optional recipient authentication.
  • Network attacker against the sidecar — sidecar listens on unix socket or loopback only; outbound restricted to AS JWKS host.

13.2 Out of scope

  • DoS against BentoClick, the AS, the sidecar, or CH.
  • External AS compromise.
  • Side-channel attacks on host.
  • Compromise of the customer's CH RBAC configuration.

13.3 Residual risk — on-box compromise

Component compromisedWhat attacker can doWhat they cannot do
BentoClick node Read drafts/specs in memory; replay JWTs observed in transit (TLS limits this) Mint tokens · forge identities to CH · impersonate inactive users
Sidecar process Return 200 for forged tokens it sees · return permissive settings in the JSON body Originate impersonated queries (if network rules block sidecar→CH initiation) · forge tokens accepted by other validators (BentoClick's own resource-server) · grant roles the user isn't actually granted (roles come from URL + CH RBAC, not from the sidecar response)
External AS Issue tokens for any user (out of scope)

This is meaningfully smaller than a design where BentoClick mints data-plane tokens.

13.4 Layered mitigations

  1. CH-side <networks> per user — even valid impersonation attempts are rejected from outside known CIDRs.
  2. Role-metadata whitelist + DEFAULT ROLE NONE + no-direct-grants — privilege ceiling is operator-curated, not gateway-controlled.
  3. Out-of-band audit witness — every sidecar 200 also writes to an append-only sink the sidecar cannot mutate after writing. Detection, not prevention; bounds dwell time.
  4. Short AS-issued JWT TTLs — ≤ 1h, with rotation.

15. Deployment shape

16. Migration from altinity-mcp

Existing altinity-mcp deployments upgrade by:

  1. Bumping to the BentoClick-branded binary (same Go module tree, new packages enabled).
  2. Adding control-plane CH configuration (separate from customer CH connections).
  3. Running BentoClick schema migrations against the control-plane CH.
  4. Optionally enabling the dashboard surface via bentoclick.dashboards.enabled=true (off by default for pure-MCP deployments).
  5. Optionally deploying the JWT verifier sidecar alongside customer OSS CH clusters that should switch to AS-validated JWT auth.

The existing MCP tool surface, OAuth resource-server config, cluster_secret flow (for deployments that keep it), and role-metadata table are unchanged. A pure-MCP deployment that never enables the dashboard surface remains functionally identical to today's altinity-mcp.

18. Open discussion items

  1. Consent-screen role picker — Auth0 (Actions limited), Keycloak (SPI), Rauthy (small patch). Which AS becomes the reference deployment for v0.2? The AS needs to mint a JWT carrying the picked role as either a groups claim (Antalya native path) or a deployment-specific claim the MCP server reads (OSS path).
  2. Expose role selection as an MCP tool argument? — currently the MCP server pins the consent role and the agent has no choice. Could expose a role: enum [...] tool argument restricted to the consent set, letting agents narrow further (e.g. drop write capability for read-only tasks). Lean: pin in v0.2, expose later if demand surfaces.
  3. Native-protocol role binding for Python clickhouse-driver — SET ROLE after connect works but interacts badly with connection pools. Document the gotcha or push users to HTTP-mode clients only?
  4. Recipient authentication on share links — required by default, or allow bearer share links as a connection-level option?
  5. Distributed lock TTL handling — KeeperMap rows don't auto-expire. Heartbeat from holder, or watchdog reaper?
  6. EXPLAIN-as-validation policy — always on publish, only on explicit validate, or per-deployment toggle?
  7. Audit-witness sink choice — object-store with object-lock vs. separate Keeper ensemble. Different recovery and tamper-evidence properties.
  8. JDBC token-helper UX — file-on-disk vs unix-socket helper vs in-driver auth-provider extension as the v0.2 default.
  9. Superset / Grafana per-user identity — accept service-identity for v0.2, defer per-user to a later milestone?
  10. Dashboard ownership transfer on user removal — admin-mediated reassignment vs. orphan-with-flag.
  11. Rendering-path policy per share — defaults in §8.1 are a starting point. May need per-deployment overrides (some operators won't want browser-direct-to-CH at all due to network posture; some won't want snapshot storage due to data sensitivity).
  12. Snapshot size and retention caps — share_snapshots needs hard limits to avoid an attacker creating shares of huge result sets to fill control-plane CH. Bytes-per-snapshot, snapshots-per-dashboard, total-bytes-per-org.
  13. Multi-audience token-helper shape — does the helper proactively refresh all known audiences in the background, or fetch lazily? Lazy is simpler; proactive avoids first-query latency.
  14. CORS configuration for browser-direct-to-CH — operators must allow the BentoClick SPA origin on every customer CH HTTP endpoint. Worth shipping a tested CH config snippet alongside the deployment docs.
  15. v1.x tenancy migration plan — when org/team/folder lands, what does the migration from org_id='default' populated rows look like? Sketch the path now to avoid painful surprises.
